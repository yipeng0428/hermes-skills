## 概述

四种模式（闪电/辩论/专家/终审）协作分析同一个问题，通过多角度→交叉审查→反事实预分析的流程，逼近顶级AI回复水平。

| 模式 | 策略 | 速度 | 适用场景 |
|------|------|------|----------|
| ⚡ **闪电模式** | 3角度并行 → 1轮汇总 | 最快 | 日常决策、快速判断、头脑风暴 |
| 🐢 **辩论模式** | 3立场 → 交叉审查 → 投票表决 | 最慢 | 重要决策、方案PK、复杂问题 |
| 🚀 **专家模式** | 预设角色 → 结构化报告 | 中等 | 商业计划、项目方案、汇报文件 |
| 🏆 **终审报告** | 元分析 → 铁律共识 → 反事实预分析 | 即时 | 所有场景自动输出 |

## 第一部分：分析框架

### Step 0: 问题解构（最重要！）

**在派发子Agent前，先将大问题拆为3-5个子问题。**

按"市场/个人/执行/财务/退出"五个经典维度拆解，或按核心争议点拆解。每个子问题必须独立可回答，且注入到**所有三个子Agent的context**中。

**拆解模板**：
```
原问题：{用户问题}

解构为5个子问题：
1. 市场：{行业/赛道/竞争格局维度}
2. 个人：{个人能力/资源/优势劣势维度}
3. 执行：{落地路径/供应链/运营维度}
4. 财务：{投入产出/回本周期/ROI维度}
5. 退出：{失败预案/止损条件/退出机制维度}
```

### Step 1: 用户画像注入

从memory或session中提取用户信息：
- 基本情况（地区/职业/技能）
- 当前核心目标
- 决策风格（保守/激进/务实）
- 风险承受力
- 已有资源（技能/人脉/资金/平台账号）

### Step 2: 并行派发三个子Agent

使用 `delegate_task` 同时启动三个子Agent，所有三个子Agent必须收到：
1. 原始问题
2. 拆解后的子问题列表
3. 用户画像
4. 各自模式的具体要求

**闪电模式子Agent**:
```
goal: "执行【闪电模式】分析。
- 原始问题：{用户问题}
- 请同时回答以下5个子问题：{子问题列表}
- 用户画像：{用户画像}
请同时从以下三个角度给出犀利分析（每个角度限200字）：
1. 数据逻辑派：聚焦行业数据、转化漏斗、ROI分析、竞争格局
2. 创意内容派：聚焦差异化、视觉呈现、内容引流、IP打造
3. 批判质疑派：质疑预算可行性、执行难度、潜在风险点
最后输出一个综合汇总表，包含：具体策略、预期效果、成本估算、执行优先级（1-5）"
```

**辩论模式子Agent**（第2代升级：增加Round 3投票）:
```
goal: "执行【辩论模式】分析。
- 原始问题：{用户问题}
- 请同时回答以下5个子问题：{子问题列表}
- 用户画像：{用户画像}
请执行三轮辩论：
【第一轮】三位专家独立回答（每人限150字）：
- 风险保守派：注重成本控制、规避风险、稳步增长
- 增长激进派：主张集中资源打爆品、快速放量
- 务实执行派：注重可落地性、团队能力匹配、投入产出比
【第二轮】交叉审视与方案修改：
- 每位专家看到另两人观点后，必须修改自己第一轮的答案
- 标注"我改变了什么 / 没改变什么 / 为什么"
【第三轮】投票表决：
- 三位专家对"最优解"进行投票（可投自己）
- 少数派（0-1票）必须写出"反对意见书"（100字以内）
【最终共识】三方达成共识的核心策略（2-3条）+ 仍存在分歧的点（1-2条）+ 投票结果 + 少数派反对意见摘要 + 综合建议（200字以内）"
```

**专家模式子Agent**（第2代升级：注入用户画像+反事实预分析）:
```
goal: "执行【专家模式】分析。
- 原始问题：{用户问题}
- 请同时回答以下5个子问题：{子问题列表}
- 用户画像：{用户画像}
请输出一份专业咨询报告，包含：
1. 市场机会分析（行业数据、竞品分析、用户画像匹配度）
2. 个人优势与劣势评估（基于用户画像，分析能力/资源匹配度）
3. 产品/方向策略（差异化定位、执行路径）
4. 成本预算（精确到百元）
5. 6个月执行路线图（月度里程碑和KPI）
6. 风险评估与止损条件
7. 反事实预分析：列出3种最可能的失败模式及补救措施
8. 最终建议：做/不做/有条件地做"
```

### Step 3: 收集结果

三个子Agent完成后，将输出保存到文件中方便用户查阅：
```
E:/hermes/output/{日期}_{问题简写}_闪电模式.md
E:/hermes/output/{日期}_{问题简写}_辩论模式.md
E:/hermes/output/{日期}_{问题简写}_专家模式.md
```

### Step 4: 主持人终审报告

**基于三方输出的二次决策推理，不是简单摘要。**

```markdown
# 🏆 终审报告：{问题简写}

## 一、铁律共识（三方100%一致的战略方向）
- ✅ 铁律1：...
- ✅ 铁律2：...

## 二、核心分歧与系统裁决
| 争议点 | 立场A | 立场B | → 系统裁决 | 理由 |

## 三、最优路线图（What To Do）
### 🔥 立即执行（本周，零成本/极低成本）
### 🚀 30天内启动（需少量预算）
### 📈 90天内推进（视前期效果决定）

## 四、一句话核心战略（20字以内，能行动）

## 五、反事实预分析（如果这个方案失败了）
| 失败模式 | 最可能的触发条件 | 系统的补救措施 |

## 六、系统置信度
- **置信度**：高/中/低
- **核心不确定因素**：...
- **止损线**：如果X天内没看到Y结果，立刻停止并调整
```

**判定逻辑**:
- 三种模式一致 → 标记为"铁律"
- 两方一致 → 采纳多数，标注分歧
- 三方不一致 → 选最保守可执行方案
- 激进vs保守 → 保守方案+激进实验预算≤20%
- 预算冲突 → 推广预算不超过总预算30%

### Step 5: 用户追问迭代

如果用户追问，执行"二次终审"：理解追问焦点 → 回溯三种模式相关输出 → 针对性补充分析 → 必要时重新派发子Agent。

### Step 6: 询问后续

> "你可以选择其中一种模式深入重做，或者直接按终审报告执行。需要我针对某个环节展开更详细的SOP吗？"

### Step 7: 分析后执行桥梁（Post-Analysis Execution Bridge）

用户看完分析后常说"去吧，去执行这三个任务"。这是**主Agent直接操作Hermes工具的信号**，而不是重新派发Execute子Agent的场景。

**关键区别**：
- 分析阶段已展示的数据（cron list、error状态、脚本路径）= 执行时的target，不需要重新获取
- 简单操作（pin provider、暂停僵尸、复制脚本）直接操作Hermes工具更快更准（<3分钟 vs 派发子Agent 5-10分钟）
- 复杂执行任务才需要派发Execute子Agent

**真实案例（2026-07-15）**：
- 完成：锁定4个配置漂移cron + 修复watchdog路径 + 暂停2个僵尸任务
- 验证通过，iLink delivery失败标注为"预期内"
- 耗时<3分钟

### 批量执行模式（Batch Execution）

当需要"研究→创建多个技能"或"并行分析多个维度"时：

1. **拆解**为3-5个独立子任务
2. **并行派发** `delegate_task` + `enabled_toolsets`
3. **收集** 输出到 `E:/hermes/output/`
4. **综合** 为终审报告
5. **转化** 每个发现为 class-level 技能
6. **验证** `skills_list()` 确认注册

## 第二部分：Execute（多智能体工具联动执行）

与分析框架不同，Execute模式专注于**完成具体任务**——搜索信息、写代码、搭自动化、出报告。

### 三类执行场景

| 场景 | 子Agent分工 | 交付物 |
|------|------------|--------|
| **调研类** | 采集员(search) + 处理员(code) + 撰写员(write) | 对比报告/数据库/信息表 |
| **开发类** | 架构师 + 编码员 + 测试员 | 可运行脚本 + 文档 |
| **自动化类** | 采集员 + 处理员 + 调度员(cron) | cronjob + 监控告警 |

### 执行流程

**Step 0: 任务解构** — 将执行任务拆为操作步骤（区别于分析框架的"子问题"）

**Step 1: 用户上下文注入** — 操作系统环境、已有文件位置、技术能力、已有cronjob

**Step 2: 并行派发执行子Agent**：
```python
delegate_task(
  tasks: [
    {role: "leaf", goal: "子Agent A的任务描述", context: "用户上下文+任务要求+输出格式"},
    {role: "leaf", goal: "子Agent B的任务描述", context: "用户上下文+任务要求"}
  ],
  enabled_toolsets: ["terminal", "file", "web"]  # ← 必须包含工具集！
)
```

**采集员**: 负责信息采集、数据抓取、文件下载（web_search/web_extract/browser/terminal）
**处理员**: 负责数据清洗、代码编写、分析处理（read_file/execute_code/terminal/write_file）
**交付员**: 负责最终报告撰写、文档整理、cronjob配置（write_file/read_file/search_files）

**Step 3: 收集结果 + 主持人验收**：
□ 所有子Agent完成 □ 交付物路径可访问 □ 数据完整 □ 代码可运行 □ 文档符合要求

**Step 4: 执行摘要输出**：交付物清单 + 执行摘要 + 后续建议

### 与分析框架的对比

| 维度 | 分析框架 | 执行框架 |
|------|---------|---------|
| **目标** | 帮用户想清楚 | 帮用户做出来 |
| **子Agent角色** | 视角角色（数据派/创意派） | 操作角色（采集员/处理员） |
| **工具使用** | 只用delegate_task + write_file | terminal/file/browser/cronjob |
| **终审重点** | 裁决决策分歧 | 验收交付物质量 |
| **适用场景** | 战略决策/方案选择 | 调研/开发/自动化 |

### 参考文档 3：v2.2 Post-Analysis Execution Pattern

**场景**：用户看完分析后说"去吧，去执行这三个任务"

**正确流程**：
```
分析阶段 → 终审报告 → 用户下达执行指令
                            ↓
              [主Agent直接操作Hermes工具]
              - cronjob(action=update) — pin provider/cron配置
              - cronjob(action=pause)  — 暂停僵尸任务
              - terminal(cp/mv)       — 修复脚本路径
              - cronjob(action=run)    — 验证修复
                            ↓
              [向用户汇报每个动作状态]
```

**注意事项**：
1. 分析数据和执行上下文不隔离 — 分析阶段展示的cron list/status就是执行时的target
2. 平台硬限制标预期 — iLink 30秒冷却是平台服务端限制
3. 静默执行+汇报 — 不需要反复确认
4. 不需要子Agent执行简单操作 — 直接操作Hermes工具更快更准

**测试（2026-07-15 实际运行）**：
- 完成：锁定4个provider漂移cron + 修复watchdog路径 + 暂停2个僵尸任务
- 耗时：<3分钟（vs 派发Execute子Agent预计5-10分钟）
